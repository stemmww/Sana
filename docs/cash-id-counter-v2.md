# Cash / ID: кандидат v2, деньги в счётчике

## Решение

**Кандидат не рекомендован для замены основных весов.** Главная цель не достигнута:
деньги в счётчике после ухода руки по-прежнему обнаружены в **0 из 6** проверочных
кадров. Ошибок ID → cash стало меньше, но общий cash recall снизился.

Основные веса, Rule Engine, Event Detector, tracking и их thresholds не изменены.
Полный pipeline не запускался. Веса кандидата сохранены отдельно:
`data/cash/runs/cash_id_v2_counter_gpu/weights/last.pt`.

## Данные и разметка

- Train: **75 → 102 кадра**, 11 исходных видео; добавлено **27 кадров**.
- Из новых: **8 кадров** с видимыми деньгами в счётчике без руки, **9** с деньгами
  в руках, **12** с ID, **19** с пустым счётчиком; категории пересекаются.
- Три новых кадра полностью отрицательные для обоих классов.
- Сохранены ровно два класса: `0: cash`, `1: id_card`.
- X‑3 и X‑2 не использовались для поиска новых кадров, обучения или выбора
  checkpoint. Все 42 validation-записи, изображения, bbox и категории сохранены.
- Разметка проверена по исходным кадрам, увеличенным фрагментам и соседним
  моментам только из обучающих видео. Прямоугольники охватывают видимые части;
  металлическая пластина и корпус счётчика не размечаются как деньги.
- Разметка выполнена ассистентом и остаётся предварительной, без независимой
  проверки человеком.

## Обучение и GPU

Старт: предыдущий кандидат `cash_id_v1_run2/weights/best.pt`.
Заранее зафиксированы 20 эпох, размер 768, batch=4, seed=42, AdamW,
lr=0.001, freeze=10, AMP выключен. Использован **последний checkpoint 20-й эпохи**.
Внутренняя проверка Ultralytics выполнялась на train; её метрики не являются
результатами на 42 отложенных кадрах и не использованы для выбора кандидата.

Первоначально ошибочно использовался CPU: окружение содержало
`torch 2.14.1+cpu`, а скрипт принудительно выбирал CPU по умолчанию.
После замечания пользователя:

1. Сохранён отдельный checkpoint после пяти полных эпох.
2. Установлены официальные `torch 2.14.1+cu130` и `torchvision 0.29.1+cu130`.
3. Проверены CUDA-вычисление матриц и torchvision NMS на RTX 3050 Laptop GPU,
   4 ГБ VRAM.
4. Обучение продолжено с эпохи 6 до 20 на GPU с прежними параметрами.
5. В `app/cv/train_cash.py` устройство по умолчанию изменено на автоматический
   выбор доступной CUDA GPU; явный `--device cpu` продолжает работать.

Пять эпох CPU: 418,4 с, **83,7 с/эпоху**. Пятнадцать эпох GPU: 174,8 с,
**11,7 с/эпоху**. В этом прогоне GPU оказался примерно **в 7,2 раза быстрее**.
Это наблюдение по разным эпохам, а не отдельный аппаратный benchmark; время
разовой установки CUDA сюда не входит. Память обучения в логе — около 0,87 ГБ.

Источник установки: [официальная инструкция PyTorch](https://pytorch.org/get-started/locally/).

## Одинаковая проверка трёх моделей

Все три checkpoint заново проверены на одних и тех же **42 полных кадрах**:
29 объектов cash, 22 ID, `confidence=0.25`, `imgsz=768`, сопоставление bbox
по `IoU >= 0.5`, один прогноз на один объект. Для сохранения прежнего протокола
все три проверки выполнены одним CPU evaluator, без crop/tiling или новых порогов.
Результаты старой модели и предыдущего кандидата полностью воспроизвелись.

| Метрика | Основная старая | Предыдущий кандидат | Новый v2 |
|---|---:|---:|---:|
| Cash precision | 52,9% | 58,3% | **59,1%** |
| Cash recall | 31,0% | 48,3% | **44,8%** |
| Cash TP / FP / FN | 9 / 8 / 20 | 14 / 10 / 15 | **13 / 9 / 16** |
| Cash in hand recall | 4/10 — 40% | 3/10 — 30% | **3/10 — 30%** |
| Cash transfer recall | 4/5 — 80% | 4/5 — 80% | **4/5 — 80%** |
| Cash at/near counter recall, все состояния | 1/14 — 7,1% | 7/14 — 50% | **6/14 — 42,9%** |
| Cash в счётчике без руки | 0/6 — 0% | 0/6 — 0% | **0/6 — 0%** |
| ID → cash, ошибочных прогнозов | 3 | 2 | **0** |
| Cash FP в пустом счётчике, 28 кадров | 0 | 1 | **0** |
| ID precision / recall | — / 0% | 64,0% / 72,7% | **63,0% / 77,3%** |

Старая модель имеет только класс cash, поэтому ID precision для неё не определён.
Общий FP включает дубликаты и cash bbox с недостаточным IoU, а не только
срабатывания на посторонних предметах. ID → cash считается, когда несопоставленный
cash bbox покрывает хотя бы 50% площади размеченного ID; определение одинаково
для всех трёх моделей. FP пустого счётчика — центр несопоставленного cash bbox
внутри заранее размеченной пустой области счётчика.

На этих шести кадрах новый кандидат вообще не выдаёт cash при confidence ≥0.25.
Здесь проблема остаётся на этапе **object detection**; это не ошибка association,
recovery, зон или семантических событий. Разметка денег занимает всего 18–19 × 16
пикселей исходного кадра. Малый размер и ограниченное разнообразие train —
возможные причины; эксперимент не отделяет их влияние.

## Правильные и ошибочные детекции

[Галерея сравнений](../data/cash_id_v2/success-and-error-examples.jpg).
Пурпурный — разметка, зелёный — cash, голубой — id_card.

- `v03_01200`: деньги в руке обнаружены правильно, cash confidence около 0,36.
- `v03_00750`: ID обнаружен правильно, confidence около 0,80; ложного cash нет.
- `v03_00600`: прежний ложный cash рядом со счётчиком исчез. Но сам ID на этом
  кадре тоже пропущен: это устранение ложного прогноза, а не успешная классификация ID.
- `v03_01700`: cash найден с confidence около 0,75, но bbox расширен вверх и имеет
  IoU около 0,46. Поэтому это FP + FN при прежнем пороге 0,5; именно этот кадр
  объясняет потерю одного cash TP относительно предыдущего кандидата.
- `v03_01150`: cash в руке не прошёл сопоставление; присутствует также неверный
  прогноз id_card на деньгах. Обратная путаница cash → ID остаётся: дополнительный
  подсчёт по тому же правилу покрытия даёт 8 прогнозов у v1 и 8 у v2.
- Все шесть кадров с деньгами в счётчике без руки по-прежнему пропущены.

## Вывод и следующий эксперимент

Улучшились отрицательные примеры и ID recall. Cash in hand не ухудшился
относительно предыдущего кандидата, но остаётся ниже старой модели.
Общий cash recall и recall у счётчика ухудшились; главная подгруппа осталась 0/6.
**Расширения train в этом объёме оказалось недостаточно.**

Для следующего эксперимента имеет смысл отдельно проверить влияние масштаба:
реальные train-кропы счётчика с корректным пересчётом bbox либо большее разрешение
детектора. Это предложение, а не уже внесённое изменение. Результат должен
проверяться вместе с деньгами в руках и отрицательными примерами; по текущему
эксперименту обещать улучшение нельзя. Дополнительный независимый набор видео
нужен, чтобы отличить улучшение обобщения от подстройки под эти 42 кадра.
