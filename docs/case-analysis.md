# Разбор кейса ForteBank и план backend

Источник: полностью прочитан предоставленный `Кейс_ForteBank.docx`: разделы 1–10,
пример JSON, таблица критериев и FAQ из 35 вопросов. Это требования к конечному
решению; текущая задача пользователя — последовательно построить backend,
начиная с FastAPI, загрузки `.mov` и выдачи `job_id`. Документ не является
поручением сейчас развёртывать сервис, публиковать данные или выполнять все этапы.

## Что должно получиться в конце

Пользователь загружает видео через интерфейс, видит статус и получает один из
двух результатов: «Нарушение не обнаружено» либо «Обнаружены признаки возможных
нарушений». На одном видео может быть несколько событий. Для каждого нужны тип,
таймкод, описание видимого действия, 1–3 JPEG-кадра и правило с нормативным источником.
Это подсказка проверяющему, а не юридическое или дисциплинарное заключение.

Потребуются работающие frontend и backend, публичные URL интерфейса и API,
API-ключ для жюри, инструкция запуска, архитектура и описание моделей,
нормативных источников, категорий событий и известных ограничений.
История проверок, регистрация пользователей, пакетная загрузка и экспорт не обязательны.

## API-контракт жюри

| Метод | Путь | Поведение |
| --- | --- | --- |
| POST | `/api/v1/analyze` | `.mov` в multipart-поле `file`, ответ содержит `job_id` |
| GET | `/api/v1/jobs/{job_id}` | Статус `processing`, `done` или `failed`; при успехе результат |

Доступ к обоим методам — через `X-API-Key`. Неверный или отсутствующий ключ
должен приводить к отказу. Точный HTTP-код успешного POST и полная схема ошибки
в документе не заданы; для первого этапа выбран `201 Created`.

Формат завершённого результата:

```json
{
  "job_id": "969750d3-9c92-4c11-903a-5bb229e86a9a",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Название типа события",
      "timecode_sec": 44.2,
      "description": "Наблюдаемое действие и основание для проверки человеком",
      "evidence_frames": [
        {"timestamp_sec": 44.2, "image_base64": "/9j/4AAQ..."}
      ]
    }
  ]
}
```

Это иллюстрация формы, а не реальный результат модели. Для отсутствия нарушений
нужны `verdict: "no_violation"` и `violations: []`. Для найденных событий —
`verdict: "violation"` и непустой список. Время задаётся числом секунд от начала
видео. Кадры — JPEG в обычном base64, без префикса data URL.

По заданию недоступность сервиса или отсутствие результата за 5 минут означает
необработанное видео. В архитектуре нужно оставить запас на загрузку, очередь,
инференс и выдачу JSON, а не расходовать все 300 секунд только на модель.

## Данные и ограничения

- Не менее 40 обучающих роликов: `.mov`, примерно 29 МБ, 10–145 секунд,
  FPS от 29, без звука. В разметке есть факт нарушения и время; типы определяет команда.
- Съёмка постановочная, сверху, одна камера и одна касса; видны кассир,
  клиенты и инкассаторы. Финальная проверка включает 5+ видео, возможен другой ракурс.
- Закрытого списка категорий нет; тест может включать неизвестные типы.
  Разрешены собственные съёмки, синтетические и открытые датасеты.
- Анализ строго визуальный. Идентификация и распознавание лиц запрещены.
- Нет доступа к АБИС, банковским журналам и внутренним системам. Нельзя
  делать выводы о проводках или сверках, которые невозможно увидеть на видео.
- Все модели выполняются внутри сервиса. Передача видео, кадров и их описаний
  в облачные AI API запрещена. После получения весов обработка должна работать
  без интернета. Публичный HTTP-вход к собственной машине этому не противоречит.
- GPU и облачные кредиты организатор не предоставляет. Целевые ресурсы и время
  обработки нужно измерить до выбора способа запуска.
- Данные разрешены только в рамках хакатона. Тестовые видео нельзя использовать
  для обучения, публиковать или передавать третьим лицам. Нужны закрытое локальное
  хранение и последующее удаление; точный срок хранения документ не задаёт.
- Предобученные модели и шаблоны допускаются при лицензиях, разрешающих
  коммерческое использование. Для выбранных YOLO-кода и весов нужно проверить
  конкретную лицензию; одно название стека не подтверждает выполнение требования.

## Нормативная база и качество результата

Команда исследует открытые акты Казахстана: НБРК, adilet.zan.kz. Внутренний
регламент и готовый перечень правил не предоставляются. Нужна прослеживаемая связь
«источник → проверяемое визуальное правило → событие → кадр». Обоснования не
должны содержать выдуманные нормы или предположения о невидимых действиях.
Исследование самих правовых актов — отдельный этап, здесь они не проверялись.

| Критерий | Баллы | Следствие для backend |
| --- | --- | --- |
| Обнаружение | 25 | Сохранить корректный общий вердикт модели |
| Локализация | 15 | Не терять точность таймкода и соответствие кадру |
| Классификация | 15 | Поддержать несколько событий и категории команды |
| Обоснованность правил | 15 | Передавать описание и реальные источники |
| Устойчивость | 10 | Обрабатывать новые видео и ошибки декодирования |
| Готовность продукта | 10 | Надёжная загрузка, статусы и понятные ошибки |
| Техническое решение | 10 | Локальная, переносимая, воспроизводимая архитектура |

Оценка заявлена автоматической, по общей JSON-схеме. Критерий обнаружения считается
по вердикту на всё видео. При равенстве баллов учитывается питчинг. Шортлист
защищает решение 5 минут и отвечает на вопросы 2 минуты; презентация необязательна.
FAQ указывает дедлайн в 12:00 без даты и часового пояса — это не полноценный срок
для планирования. ForteBank оставляет право коммерческого использования решения.
FAQ отдельно упоминает дисквалификацию за облачные API или готовые решения.

## Неоднозначности, которые нужно учитывать

1. FAQ обсуждает вердикт «Недостаточно данных», но разделы 4 и 10 разрешают только
   два вердикта. Пока следуем явной схеме API: технический сбой — `failed`,
   успешный анализ — один из двух вердиктов. Не подменяем сбой `no_violation`.
   Политику для успешно декодированного, но неразборчивого видео согласуем с AI-командой.
2. Требуется источник с пунктом/разделом, но FAQ допускает ссылки без точного пункта.
   По возможности сохраняем точный пункт и URL. В JSON-примере поля источника нет:
   согласуем расширение `rule` с frontend и моделью; при необходимости включим
   источник в `description`, сохранив обязательные поля жюри.
3. Упомянуты как разрешённые шаблоны и модели, так и запрет «готовых решений».
   Используем библиотеки и модели как компоненты своего сервиса; при сомнениях
   о конкретном стороннем продукте нужна трактовка организаторов.
4. Не заданы предел файла, число параллельных загрузок, интервал polling и схема
   `failed`. Лимит первого этапа — 100 МиБ, выше ориентировочных 29 МБ; это наша настройка.
5. FAQ одновременно просит минимизировать ложные срабатывания и не допускать пропуски.
   Порог и компромисс определяются измерениями, backend не должен добавлять события
   или менять вердикты самостоятельно.

## Разделение работы

AI/CV-команда: модели, веса, предобработка, детекция/трекинг, визуальные правила,
типы событий, таймкоды, выбор доказательных кадров и измерение качества.
Нормативные основания нужно согласовать внутри команды отдельно — они обязательны,
но не возникают автоматически из детекции YOLO.

Backend: приём и проверка файлов, локальное хранение, идентификаторы задач,
очередь и worker, состояния и ошибки, валидация JSON, упаковка JPEG в base64,
ключ доступа, интеграция frontend, запуск, публичный адрес и эксплуатационные лимиты.
Нужно заранее определить, кто реализует frontend: он обязателен для сдачи.

Предлагаемая граница интеграции: обработчик получает путь к локальному видео
и возвращает структурированный результат с событиями и кадрами. Он не зависит
от FastAPI, HTTP, API-ключа и базы. Тяжёлый инференс выполняется вне HTTP-запроса.

## Последовательность реализации

1. **Текущий этап:** структура FastAPI, `POST /api/v1/analyze`, сохранение `.mov`,
   UUID, SQLite-запись, базовые ошибки и `X-API-Key`. Проверить загрузку и сохранность.
2. **Жизненный цикл:** отдельный worker и выбор очереди с учётом ресурсов;
   `GET /api/v1/jobs/{job_id}`, `processing/done/failed`, неизвестный UUID → 404,
   таймаут, ограничение параллельности и восстановление после перезапуска.
3. **Контракт результата:** Pydantic-схемы обоих вердиктов, событий, доказательств,
   источников и ошибок. Согласовать интерфейс обработчика с AI-командой.
4. **Интеграция OpenCV/YOLO:** проверка декодирования, локальные веса, реальный
   обработчик, кадры JPEG/base64, тест на размеченных видео и бюджет до 5 минут.
5. **Пользовательский сценарий:** загрузка, polling, вердикт, события, кадры и
   нормы в frontend. Держать серверный API-ключ вне публичного JS.
6. **Развёртывание:** воспроизводимые зависимости, контейнер/инструкция,
   persistent volume, публичный HTTPS, reverse proxy с лимитом тела и таймаутами,
   ограничение доступа, очистка данных и проверка внешним клиентом.
7. **Сдача:** URLs и ключ жюри, документация, архитектура, лицензии моделей,
   нормативные источники, категории и ограничения; контрольный прогон полного API.

Redis/Celery, Docker и публичный туннель не добавлены на первом этапе: способ
выполнения задач и хостинг выберем при переходе к соответствующему шагу.
Реализованы загрузка, схема результата и основа жизненного цикла: API статусов,
отдельный worker, атомарный захват, сохранение результата и таймаут с остановкой процесса.
Текущая очередь хранится в SQLite. Тесты используют синтетические обработчики.
Добавлены общий дедлайн от поступления запроса в FastAPI, ограничение числа
незавершённых задач и слотов выполнения, резервирование места до постоянного
сохранения файла и HTTP `503 / QUEUE_FULL` при перегрузке. Просроченные задачи
завершаются без AI-worker благодаря фоновому проходу API. Добавлены проверка
ключа до чтения тела, лимиты входящего потока и размера файла во время разбора,
таймаут ожидания тела и очистка временных файлов при обрывах. Ограничения
и буферизация reverse proxy остаются частью подготовки публичного запуска;
серверный бюджет сам по себе не гарантирует доставку результата жюри за 5 минут.
Подключение реального AI-обработчика и согласование схемы с командой ещё впереди:
[ai-integration.md](ai-integration.md). Без настроенного обработчика задачи
остаются в ожидании (`processing`) до истечения общего срока, затем `failed`.
В БД это внутреннее `uploaded`; автоматического фиктивного результата нет.

Добавлена настраиваемая очистка завершённых задач, видео и рабочих файлов;
по умолчанию хранение составляет 24 часа после завершения, затем API возвращает
`404`. Это техническая настройка команды, срок из кейса не определён.
Очистка активных задач не выполняется; токен worker дополнительно защищает
ещё занятые файлы, а файлы без записи удаляются после защитного периода.
Есть ручной проход и `--dry-run`; правила и короткий тест описаны в README.
